# SLOs

Notes for myself on why the SLOs look like this. Mostly based on the
[SRE book](https://sre.google/sre-book/service-level-objectives/) and the
[SRE workbook chapter on alerting](https://sre.google/workbook/alerting-on-slos/).

## SLI vs SLO vs SLA (short version)

- **SLI** – a measurement. Here: "fraction of probes that got a good response".
- **SLO** – the target for the SLI over a time window. Here: 99.9% over 30 days.
- **SLA** – a contract with consequences (money back etc). These sites don't have one,
  so there are only SLOs.

## The SLIs

Both come from the prober, which hits every site every 30 seconds from outside
(like a user would).

| SLI | good event | bad event |
|---|---|---|
| availability | HTTP 2xx/3xx **and** the expected text is on the page | 4xx/5xx, timeout, connection error, wrong content |
| latency | response faster than 1.5 s | response slower than 1.5 s |

Checking the expected text matters: a hosting "account suspended" page also returns 200.

TLS and DNS are **not** part of the availability SLI. A certificate that expires in 10 days
doesn't hurt anybody yet, so it has its own alert (`TLSCertExpiringSoon`) instead.

## The SLOs

Configured in [`slos.yaml`](slos.yaml).

### Availability: 99.9% over 30 days

That's **43.2 minutes** of downtime per month. These are small sites on normal hosting, so
99.99% (4.3 min) is not realistic: one hosting restart would break it. 99% (7.2 hours) would
be too loose to notice real problems.

### Latency: 90% of responses under 1.5 s

My first idea was "95% under 500 ms", but I measured it first (≈30 min of data from my home
network):

| site | < 0.5 s | < 0.75 s | < 1.5 s |
|---|---|---|---|
| kuponradar | 72.7% | 93.7% | 96.8% |
| taxnieruchomosci | 23.7% | 72.7% | 96.8% |
| alstrategika | 19.0% | 42.9% | 93.7% |

With 500 ms the SLO would be broken from day one, and an SLO that's always red is useless
because everyone learns to ignore it. 1.5 s at 90% is achievable now, and still catches
the site getting noticeably slower. The plan is to tighten it once I have more data and
can probe from a server instead of my home wifi.

The threshold has to be one of the histogram buckets in `prober/metrics.py`
(Prometheus can only count "faster than X" for bucket boundaries).

## Error budget

`error budget = 1 - SLO`. For 99.9% it's 0.1% of probes = 43.2 min/month.

As long as there's budget left, it's fine to deploy, experiment etc. When it's gone, the
idea is to stop risky changes and work on reliability instead.

Remaining budget is on the Grafana dashboard ("Error budget remaining" and
"Downtime left this month").

## Alerting: multi-window, multi-burn-rate

Alerting on every failed probe would be really noisy: one timeout from my wifi isn't
an incident. Instead, alerts fire based on **burn rate**, i.e. how fast we're using the budget.
Burn rate 1 = the budget would last exactly 30 days.

| severity | long window | short window | burn rate | budget used when it fires |
|---|---|---|---|---|
| page | 1h | 5m | 14.4× | 2% |
| page | 6h | 30m | 6× | 5% |
| ticket | 1d | 2h | 3× | 10% |
| ticket | 3d | 6h | 1× | 10% |

- The **long window** makes sure it's a real problem and not a blip.
- The **short window** makes the alert stop quickly once the problem is fixed
  (otherwise a 1h window keeps the alert firing for an hour after recovery).

Rules are generated by [`rules.py`](rules.py) (3 sites × 2 SLOs × 8 windows was way too much
to write by hand), and tested with `promtool test rules`
([`deploy/prometheus/tests/slo_test.yml`](../deploy/prometheus/tests/slo_test.yml)):

1. one failed probe → no alert
2. site fully down for 10 min → page
3. constant 0.5% errors (5× burn) → ticket but no page
4. prober down → page
5. cert with 10 days left → ticket

```bash
python -m slo.rules > deploy/prometheus/rules/slo.rules.yml   # after changing slos.yaml
```

### A 90% SLO can't use the 14.4× alert

With a 90% objective the budget is 10%, so 14.4× burn means a 144% error ratio, which is
impossible. The generator skips conditions whose threshold is ≥ 1, so the latency page alert
only uses the 6h/30m (6×) window.

## Known limitations

- **Little history = noisy long windows.** Right after Prometheus starts, the "6h" window
  has maybe an hour of data, so a single failure looks much worse than it is. I hit this in
  the promtool tests: one failed probe paged with 75 min of history but not with 3 days.
- **One vantage point.** All probes come from one place. If my network breaks, every site
  looks down. Probing from 2-3 regions is planned (week 6).
- **Probe resolution.** One probe every 30 s, so a 10-second outage can be missed completely,
  and one failed probe counts as ~30 s of downtime.
- **Prober down = no data.** If the prober dies, the SLO can't see anything. That's what the
  `ProberDown` alert is for.
- **Latency includes my ISP.** Measured from home, not from where real users are.
